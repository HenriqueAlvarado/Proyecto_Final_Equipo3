3. ERRORES ENCONTRADOS Y TIEMPO DE RESOLUCION
================================================================================

Se documentaron 15 errores durante el desarrollo. A continuacion se presentan
con su clasificacion, impacto y tiempo de resolucion.

Clasificacion de severidad:
  CRITICO  - Bloquea funcionalidad principal del sistema
  ALTO     - Afecta una funcionalidad importante
  MEDIO    - Afecta experiencia de usuario o flujo secundario
  BAJO     - Problema menor o de configuracion

--------------------------------------------------------------------------------
ERR-01 | IP Carrier-Grade NAT no accesible desde internet
--------------------------------------------------------------------------------
Severidad:    CRITICO
Componente:   Infraestructura AWS (EC2)
Descripcion:  AWS Academy asigno IP 100.31.109.89 (rango CGN) que no es
              accesible desde internet externo. Dispositivos externos no
              podian conectarse al backend.
Tiempo deteccion:  Inmediato al intentar acceder desde celular
Tiempo resolucion: 30 minutos
Solucion:     Asignar Elastic IP fija (3.219.251.228)
Recurrencia:  No (solucion permanente)

--------------------------------------------------------------------------------
ERR-02 | CORS con origin "*" como string no funciona con credentials
--------------------------------------------------------------------------------
Severidad:    CRITICO
Componente:   Backend (src/index.js)
Descripcion:  Express rechaza el string "*" en la opcion origin cuando
              credentials: true esta activo. El frontend recibia timeout.
Tiempo deteccion:  Al hacer primera peticion desde el frontend
Tiempo resolucion: 20 minutos
Solucion:     Usar funcion callback: origin: (origin, cb) => cb(null, true)
Recurrencia:  No

--------------------------------------------------------------------------------
ERR-03 | Build de React con IP vieja quemada en cache
--------------------------------------------------------------------------------
Severidad:    ALTO
Componente:   Frontend (proceso de build)
Descripcion:  Al cambiar REACT_APP_API_URL en .env, el build seguia usando
              la IP anterior porque react-scripts cachea el bundle.
Tiempo deteccion:  Al verificar que el frontend seguia apuntando a IP vieja
Tiempo resolucion: 5 minutos
Solucion:     Eliminar carpeta build/ antes de npm run build
Recurrencia:  2 veces (cada cambio de IP)

--------------------------------------------------------------------------------
ERR-04 | Race condition en redirect de paciente tras login
--------------------------------------------------------------------------------
Severidad:    ALTO
Componente:   Frontend (AuthContext, LoginPage)
Descripcion:  Al hacer login como paciente, el sistema mostraba pagina 404.
              LoginPage detectaba el usuario y hacia <Navigate to="/mis-citas">,
              pero ProtectedLayout ejecutaba su render antes de que el contexto
              se actualizara, viendo user como null y redirigiendo a /login,
              creando un loop que terminaba en 404.
Tiempo deteccion:  Al probar login de paciente por primera vez
Tiempo resolucion: 45 minutos
Solucion:     Usar useNavigate() directamente en los formularios de login
              en lugar de depender del redirect del LoginPage.
Recurrencia:  No

--------------------------------------------------------------------------------
ERR-05 | Codigo duplicado en pacientes.routes.js
--------------------------------------------------------------------------------
Severidad:    CRITICO
Componente:   Backend (pacientes.routes.js)
Descripcion:  El archivo tenia dos bloques de rutas y dos module.exports.
              El segundo sobreescribia al primero, dejando todas las rutas
              de pacientes sin registrar en Express.
Sintoma:      Todos los endpoints /api/pacientes retornaban 404.
Tiempo deteccion:  Al probar endpoints de pacientes
Tiempo resolucion: 30 minutos
Solucion:     Reescritura completa del archivo con estructura limpia
Recurrencia:  No

--------------------------------------------------------------------------------
ERR-06 | sendAppointmentEmail no enviaba correo (datos faltantes)
--------------------------------------------------------------------------------
Severidad:    ALTO
Componente:   Backend (citas.routes.js)
Descripcion:  El INSERT de citas devuelve solo IDs (paciente_id, medico_id).
              El email.service.js necesita paciente_email y paciente_nombre
              que llegaban como undefined, por lo que el correo nunca se enviaba.
Tiempo deteccion:  Al revisar logs de PM2 tras configurar SendGrid
Tiempo resolucion: 15 minutos
Solucion:     Query adicional despues del INSERT para obtener datos completos
Recurrencia:  No

--------------------------------------------------------------------------------
ERR-07 | SendGrid 403 Forbidden - sender no verificado
--------------------------------------------------------------------------------
Severidad:    ALTO
Componente:   Backend (email.service.js) + configuracion SendGrid
Descripcion:  SENDGRID_FROM estaba configurado como noreply@clinicasanangel.com
              que no es un sender verificado en SendGrid. La API retorna 403
              si el remitente no esta verificado como Single Sender.
Tiempo deteccion:  Al revisar logs tras primer intento de envio
Tiempo resolucion: 10 minutos
Solucion:     Actualizar SENDGRID_FROM al email verificado en SendGrid
Recurrencia:  No

--------------------------------------------------------------------------------
ERR-08 | git pull no actualiza archivos en EC2 via SSM (permisos root)
--------------------------------------------------------------------------------
Severidad:    MEDIO
Componente:   Proceso de deploy (EC2)
Descripcion:  SSM ejecuta comandos como root. El repo fue clonado por ec2-user.
              git pull como root no actualiza los archivos del repo de ec2-user.
Tiempo deteccion:  Al verificar que el backend seguia con codigo viejo
Tiempo resolucion: 20 minutos
Solucion:     Usar SSH directo con ec2-user en lugar de SSM para git pull
Recurrencia:  Cada reinicio del lab (solucion: siempre usar SSH)

--------------------------------------------------------------------------------
ERR-09 | CloudFront no disponible en AWS Academy
--------------------------------------------------------------------------------
Severidad:    MEDIO
Componente:   Infraestructura (CloudFront)
Descripcion:  AWS Academy no permite crear distribuciones CloudFront.
              El frontend no puede servirse por HTTPS.
Impacto:      Chrome movil fuerza HTTPS y bloquea la pagina.
Tiempo deteccion:  Al intentar configurar HTTPS
Tiempo resolucion: N/A (limitacion del entorno, no tiene solucion en AWS Academy)
Solucion adoptada: Usar Firefox o Samsung Internet que respetan HTTP.
Recurrencia:  Permanente (limitacion del entorno)

--------------------------------------------------------------------------------
ERR-10 | PM2 pierde procesos al reiniciar el laboratorio
--------------------------------------------------------------------------------
Severidad:    BAJO
Componente:   Infraestructura (EC2 + PM2)
Descripcion:  Cada vez que el lab de AWS Academy se pausa y reinicia,
              PM2 no recupera automaticamente los procesos aunque se haya
              ejecutado pm2 save. El EC2 reinicia completamente.
Tiempo deteccion:  Al primer reinicio del lab
Tiempo resolucion: 2 minutos (levantar manualmente)
Solucion:     Procedimiento documentado: conectar por SSH y ejecutar
              pm2 start src/index.js --name medisync-api
Recurrencia:  Cada reinicio del lab

--------------------------------------------------------------------------------
ERR-11 | IP del EC2 cambia al reiniciar el lab
--------------------------------------------------------------------------------
Severidad:    ALTO (antes de la solucion)
Componente:   Infraestructura (EC2)
Descripcion:  Sin Elastic IP, cada reinicio del lab asignaba una nueva IP
              al EC2, requiriendo rebuild del frontend.
Tiempo deteccion:  Al segundo reinicio del lab
Tiempo resolucion: 30 minutos (asignar Elastic IP)
Solucion:     Elastic IP fija 3.219.251.228 (solucion permanente)
Recurrencia:  No (solucion permanente)

7. DEUDA TECNICA IDENTIFICADA
================================================================================

La siguiente deuda tecnica fue identificada durante el desarrollo pero no
se implemento por limitaciones de tiempo del proyecto de laboratorio.
Se documenta para transparencia y mejora futura.

DT-01 | Sin HTTPS en el frontend
  Impacto:    Medio - Chrome movil fuerza HTTPS
  Causa:      CloudFront no disponible en AWS Academy
  Solucion:   Migrar a un proveedor que soporte HTTPS (Vercel, Netlify,
              o AWS fuera del lab)

DT-02 | CORS abierto para todos los origenes
  Impacto:    Bajo (entorno de laboratorio)
  Causa:      IPs dinamicas del lab y S3 HTTP requieren flexibilidad
  Solucion:   En produccion real, restringir a dominio especifico del frontend

DT-03 | Sin TypeScript
  Impacto:    Bajo - mayor riesgo de errores de tipo en runtime
  Causa:      Decision de velocidad de desarrollo
  Solucion:   Migrar gradualmente a TypeScript en version futura

DT-04 | Sin pruebas de integracion end-to-end
  Impacto:    Medio - flujos completos no estan automatizados
  Causa:      Limitacion de tiempo
  Solucion:   Agregar Cypress o Playwright para pruebas E2E

DT-05 | PM2 sin startup automatico
  Impacto:    Bajo (solo afecta reinicios del lab)
  Causa:      pm2 startup requiere permisos de root en EC2
  Solucion:   Ejecutar pm2 startup y seguir las instrucciones generadas

DT-06 | Sin reporte de cobertura de lineas
  Impacto:    Bajo - no se puede medir cobertura exacta
  Causa:      Limitacion de tiempo
  Solucion:   Agregar jest --coverage al script de test
